5. Basis of preparation and limitations

  • Point in time. Holdings are stated as of {{ r.period.end.time_utc | utc }} (block {{ r.period.end.height }}); nothing here says what the wallet holds after that.
  • Control, not title. A proof shows that the keys behind an address signed the message. It does not show who owns the coins, whether they are pledged, lent or otherwise encumbered, or what liabilities stand against them.
  • Completeness. The movements and holdings are those of this wallet as known to the holder's node. That the wallet is the holder's only one, or that all of its addresses are in the node, rests on the holder's representation; no cryptographic check establishes it.
  • Proofs are per address. An address proven once is covered for every coin paid to it. The date of each proof is the block named in its message; section 3 says for each address whether the proof postdates the period.
  • No wallet structure is disclosed. The statement and the bundles name addresses and outputs only; they carry no descriptor, extended public key or derivation path.

  • Fiat values are informational, from rates the holder supplied ({{ r.fiat.source }}), at the rate in force on each transaction's day.

6. Verification procedures

Every figure and proof above is checkable on any Bitcoin node with the chain, without a wallet or an index.

  1. Proof of control, per address. Run the verify command printed under the address in section 3; it prints what is printed here, starting with VALID. Paste it as it stands: the backslashes continue the command across lines, and the message keeps its own line break inside the quotes. For a second opinion, bip322-refcheck ADDRESS PROOF MESSAGE runs independent implementations beside it, and bitcoin-cli getblockheader HASH with the hash from the message's last line confirms the block's height and time.
  2. Holdings, per output. Run the on chain command printed under each output in section 4 (a direct lookup, instant). An output spent after the period's end no longer shows; report.json names the transaction that spent it. The same by address, bip322 audit holdings ADDRESS --at BLOCK, scans the whole UTXO set and takes minutes on a mainnet node.
  3. Movements. Each transaction in section 2 by txid; the running balance follows from the opening balance and the net of each.
  4. All of it at once. The proofs come as files next to this statement{% if r.bundles %}: {% for b in r.bundles %}ledger/{{ b.bundle }}{% if not loop.last %}, {% endif %}{% endfor %}{% endif %}. bip322-audit verify FILE checks every proof in a file, its stamp block, and that every output the file lists existed at that block. report.json carries every figure of this statement and its reference {{ r.report_id }}. Both tools install with pip install bip322-reports.
