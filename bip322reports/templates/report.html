4. Basis of preparation and limitations

Amounts. BTC, exact to eight decimals (1 BTC = 100 000 000 satoshi); negative amounts in parentheses{% if r.fiat %}; {{ r.fiat.currency }} values from {{ r.fiat.source }}{% endif %}.

Point in time. Opening figures are as of the period's first block, closing figures as of its last, block {{ r.period.end.height }} ({{ r.period.end.time_utc | utc }}){% if r.period.to_tip %}, the chain tip when the statement was prepared{% endif %}; nothing here says what the wallet holds after that.

Wallet. {{ r.label }}{% if r.policy %}, addresses controlled by {{ r.policy }} keys{% endif %}, on the {{ r.chain }} chain. Prepared {{ r.generated_utc | utc }} by {{ r.tool }}; reference {{ r.report_id }}, derived from the figures stated.

Control, not title. A proof shows that the keys behind an address signed the message. It does not show who owns the coins, whether they are pledged, lent or otherwise encumbered, or what liabilities stand against them.

Completeness. The movements and holdings are those of this wallet as known to the holder's node. That the wallet is the holder's only one, or that all of its addresses are in the node, rests on the holder's representation; no cryptographic check establishes it.

Scripts, addresses and UTXOs. BIP-322 defines a proof for a scriptPubKey, "the key script to be proven"; an address is that script, checksummed and encoded, and the proof is not about any particular coin. Coins are UTXOs, each locked to exactly one scriptPubKey, which the node reports. Each page of section 3 reads the UTXO's scriptPubKey from the chain and runs the verifier on those same bytes; control of the script is therefore control of the UTXO. A script proven once is covered for every UTXO paid to it, before or after the proof; the date of each proof is the block named in its message.

No wallet structure is disclosed. The statement and the bundles name addresses and outputs only; they carry no descriptor, extended public key or derivation path.

    • 5. Verification procedures

    Every figure and proof above is checkable on any Bitcoin node with the chain, without a wallet or an index. Section 6 explains what a proof is.

    Proof of control, per UTXO. Run the verify command printed on the UTXO's page in section 3; its first argument is the scriptPubKey, the same bytes the lookup below it reports for the UTXO; it prints what is printed here, starting with VALID and ending with the tool and specification it ran under. Paste it as it stands: the backslashes continue the command across lines, and the message keeps its own line break inside the quotes. For a second opinion, bip322-refcheck ADDRESS PROOF MESSAGE runs independent implementations beside it, and bitcoin-cli getblockheader HASH with the hash from the message's last line confirms the block's height and time.

    Holdings, per UTXO. Run the lookup command printed on the UTXO's page (a direct lookup, instant); its --at is the block named in the proof's message, so control and holding are checked at one block. Its "locked to" line is the scriptPubKey the proof is verified against; the address beneath it is the same bytes encoded, and bip322 validateaddress or bitcoin-cli validateaddress converts between the two. To look inside a proof, bip322 decodesignature PROOF --text shows the witness script it carries and derives the scriptPubKey from it. An output spent after the period's end no longer shows; {{ r.name | default("report") }}.json names the transaction that spent it. The same by address, bip322 audit holdings ADDRESS --at BLOCK, scans the whole UTXO set and takes minutes on a mainnet node.

    Movements. Each transaction in section 1 by txid; the running balance follows from the opening balance and the net of each.

    All of it at once. The proofs come as files next to this statement{% if r.bundles %}: {% for b in r.bundles %}ledger/{{ b.bundle }}{% if not loop.last %}, {% endif %}{% endfor %}{% endif %}. bip322-audit verify FILE checks every proof in a file, its stamp block, and that every output the file lists existed at that block. {{ r.name | default("report") }}.json carries every figure of this statement and its reference {{ r.report_id }}.     6. How a proof of control works

    {% set m = t.muted %}{% set k = t.ink %}{% set st = t.strong %}{% set ln = t.rule_strong %}

    A proof of control is a spend of the scriptPubKey that can never happen: the coin it spends does not exist, but the witness is the one a real spend would need. The same scriptPubKey locks the UTXO on the chain.

    Coins and scripts. A bitcoin balance is a set of unspent transaction outputs, UTXOs. Each carries an amount and a lock, its scriptPubKey: the script a spending transaction must satisfy, typically with signatures from particular keys. For a multisignature wallet the lock is a hash of the script that names the keys and the threshold ({{ r.policy or "m of n" }}); whoever can satisfy that script controls every UTXO locked to it. Control is therefore a property of the scriptPubKey, and that is what a proof is about.

    The message. The signers sign the text shown on each UTXO page: a title and a line naming a block by height, hash and time. The hash of a block cannot be known before the block exists, so a proof over it cannot have been made earlier; the block is the proof's date.

    The virtual transactions. BIP-322 turns the message into two transactions that never reach the network. The first, "to_spend", has one input that commits to the message (its script carries a tagged hash of the text, tag BIP0322-signed-message) and one output of zero value locked to the scriptPubKey being proven. The second, "to_sign", spends that output to an unspendable output. The first spends nothing that exists, so neither can ever be confirmed: a proof cannot move funds.

    The proof. The proof is the witness of "to_sign": exactly the signatures and, for a multisignature script, the script itself, that a real spend of a UTXO locked to the same scriptPubKey would require. It is encoded in base64 with the prefix smp, BIP-322's simple format. For a P2WSH lock the scriptPubKey is the SHA-256 of the script the proof carries; that is the link between the proof and the chain.

    Verification. A verifier rebuilds the two transactions from the message and the scriptPubKey, attaches the witness, and runs the consensus script engine as a node would on a real spend. VALID means the keys that control the script signed this message. The engines named in the output are independent implementations of that check, one of them Bitcoin Core's own consensus library.

    What it shows. That at the block named in the message the holder could produce a valid spend from the scriptPubKey, which is what controlling the UTXOs locked to it means. It does not show ownership, and it says nothing about any later time; a new proof over a new block does.
