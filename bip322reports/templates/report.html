4. How a proof of control works

{% set m = t.muted %}{% set k = t.ink %}{% set st = t.strong %}{% set ln = t.rule_strong %}{% set mono = t.font_mono | safe %} {% set amount = r.closing.coins[0].amount_btc if r.closing.coins else "0.10000000" %}

A proof of control is a spend from the scriptPubKey that can never happen: the coin it spends does not exist, but the witness is the one a real spend would need, and the same scriptPubKey locks the UTXO on the chain.

Coins and locks. A balance is a set of unspent transaction outputs, UTXOs. Each carries an amount and a scriptPubKey, the condition a transaction spending it must meet. This wallet's condition is P2WSH: the scriptPubKey is OP_0 <SHA-256 of a witness script>, and the witness script says that {{ r.policy or "m of n" }} named public keys must sign. Whoever can meet the condition controls every UTXO locked to it, so control is a property of the scriptPubKey, and that is what a proof is about.

The message. The text shown on each UTXO page: a title line, and a line naming a block by height, hash and time. The hash of a block cannot be known before the block exists, so the proof is no older than that block. The verifier hashes the message with SHA-256 under the tag BIP0322-signed-message.

to_spend. Version 0, locktime 0. One input, spending the null outpoint (txid all zeros, index ffffffff), which no transaction has ever created; its scriptSig is OP_0 followed by the 32-byte hash of the message; sequence 0. One output of 0 satoshi with the scriptPubKey being proven. The transaction's id follows from the message and the scriptPubKey alone.

to_sign. Version 0, locktime 0. One input spending to_spend's output 0, sequence 0; one output of 0 satoshi to OP_RETURN, which nothing can spend. The input's witness is what the signers produce: for this wallet an empty element, {{ r.policy.split(" of ")[0] if r.policy else "m" }} signatures, and the witness script that names the {{ r.policy.split(" of ")[1] if r.policy else "n" }} keys; the same stack a real spend from the scriptPubKey carries. Each signature commits to to_sign, hence to to_spend's id, hence to the message.

The proof. That witness, serialised as in a transaction and base64-encoded with the prefix smp (BIP-322's simple format, v2.0.0). Nothing else needs to be kept: the verifier rebuilds both transactions from the message and the scriptPubKey.

Verification. The verifier rebuilds to_spend and to_sign, puts the witness on to_sign's input, and runs the consensus script engine on it exactly as a node validating a block would: the witness script must hash to the value in the scriptPubKey, the signatures must verify against keys the script names over to_sign's signature hash, and the threshold must be met. The engines named in each output do this independently; one of them is Bitcoin Core's own consensus library. Neither transaction spends a coin that exists, so neither can ever be confirmed: a proof cannot move funds.

What it shows. That at the block named in the message the holder could produce a valid spend from the scriptPubKey, which is what controlling the UTXOs locked to it means; a UTXO confirmed after that block is covered by a later proof. Control, not title: not who owns the coins, nor what liabilities stand against them. Nothing about any time after the block; a new proof over a new block does.
