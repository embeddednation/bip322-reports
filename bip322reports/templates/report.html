4. How a proof of control works

{% set m = t.muted %}{% set k = t.ink %}{% set st = t.strong %}{% set ln = t.rule_strong %}{% set mono = t.font_mono | safe %}{% set tile = t.tile %} {% macro val(x, y, text, role) -%} {{ text }} {%- endmacro %} {% macro pill(x, y, w, text, size=8.5) -%} {{ text }} {%- endmacro %} {% macro field(x, y, name, value, role=None) -%} {{ name }}{% if role %}{{ val(x + (name | length + 1) * 5.4, y, value, role) }}{% else %}{{ value }}{% endif %} {%- endmacro %} {% macro txbox(x, y, title, sub) -%} {{ title }} {{ sub }} {%- endmacro %}

A proof of control is a spend from the scriptPubKey that can never happen: the coin it spends does not exist, but the witness is the one a real spend would need. On the chain, a real transaction pays an amount to the same scriptPubKey; that output is the UTXO the statement counts. The mechanism is the same for every kind of scriptPubKey.

{% set S = 'scriptPubKey' %} {% set H = 'hash of the message' %} {% set X = 'txid of to_spend' %} {% set P = 'proof' %} {% set U = 'UTXO' %} {% set B = 'block' %}

Coins and locks. A balance is a set of unspent transaction outputs, {{ U | safe }}s. Each carries an amount and a {{ S | safe }}, the condition a transaction spending it must meet. The condition can be of any kind the network accepts: a signature from one key (pay to a public key hash), whatever a script demands (pay to a script hash), a taproot output. A {{ U | safe }} comes into being when a real transaction, with inputs and outputs like any other, pays an amount to a {{ S | safe }}; it is named by that transaction's id and the output's index. Whoever can meet the condition controls every {{ U | safe }} locked to it, so control is a property of the {{ S | safe }}, and that is what a proof is about. This wallet's {{ S | safe }}s are pay-to-witness-script-hash: OP_0 <SHA-256 of a witness script>, the witness script requiring signatures from {{ r.policy or "m of n" }} named keys.

The message. The text shown on each {{ U | safe }} page: here a title line, and a line naming a {{ B | safe }} by height, hash and time. The hash of a block cannot be known before the block exists, so the proof is no older than that {{ B | safe }}. The message is hashed with SHA-256 under the tag BIP0322-signed-message, giving the {{ H | safe }}, which is what enters the transactions.

to_spend. Version 0, locktime 0. One output of 0 satoshi with the {{ S | safe }} being proven: the lock, with nothing in it. One input spending the null outpoint (txid all zeros, index ffffffff), which no transaction has ever created, with sequence 0 and a scriptSig of OP_0 followed by the {{ H | safe }}. Like every transaction it has an id, SHA-256 taken twice over its bytes, the {{ X | safe }}; since those bytes are fixed by the message and the {{ S | safe }}, so is the id.

to_sign. Version 0, locktime 0. One input whose prevout is the {{ X | safe }} and output index 0, sequence 0; one output of 0 satoshi to OP_RETURN, which nothing can spend. The input's witness is what the signers produce, and it is exactly the unlocking data a real spend from the {{ S | safe }} would carry: for a single-key lock, one signature; for this wallet, {{ r.policy.split(" of ")[0] if r.policy else "m" }} signatures and the witness script naming its {{ r.policy.split(" of ")[1] if r.policy else "n" }} keys. Each signature commits to to_sign, hence to the {{ X | safe }}, hence to the {{ H | safe }} and the message.

The {{ P | safe }}. That witness, serialised as in a transaction and base64-encoded with the prefix smp (BIP-322's simple format, v2.0.0). Nothing else needs to be kept: the verifier rebuilds both transactions from the message and the {{ S | safe }}.

Verification. The verifier rebuilds to_spend from the {{ H | safe }} and the {{ S | safe }}, rebuilds to_sign from the {{ X | safe }} with the {{ P | safe }} as its witness, and runs the consensus script engine on that input exactly as a node validating a block would: the {{ P | safe }} must unlock the {{ S | safe }} under the same rules that govern every spend on the network, whatever kind of lock it is; for this wallet, the script must hash to the value in the {{ S | safe }} and enough of the keys it names must have signed. The engines named in each output do this independently; one of them is Bitcoin Core's own consensus library. Neither transaction spends a coin that exists, so neither can ever be confirmed: a {{ P | safe }} cannot move funds. That is the verify command on each {{ U | safe }} page; the lookup beside it is the fourth step, finding the {{ U | safe }} in the chain's set of unspent outputs, with its amount and the same {{ S | safe }} bytes the {{ P | safe }} was verified against.

What it shows. That at the {{ B | safe }} named in the message the holder could produce a valid spend from the {{ S | safe }}, which is what controlling the {{ U | safe }}s locked to it means; a {{ U | safe }} confirmed after that {{ B | safe }} is covered by a later {{ P | safe }}. Control, not title: not who owns the coins, nor what liabilities stand against them. Nothing about any time after the {{ B | safe }}; a new {{ P | safe }} over a new {{ B | safe }} does.
